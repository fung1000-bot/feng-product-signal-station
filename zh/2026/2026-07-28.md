# 枫的产品信号站 - 2026-07-28

## 今日主判断

AI 编程的竞争重点正在从“能不能生成代码”转向“能不能替用户完成真实交付”；最值得验证的是一个面向中文 AI 编程用户的低摩擦屏幕上下文工具，而不是再做一个泛 AI 生成器。

## 今日最值得做的一个方向

**项目名：** 指哪问哪：面向 AI 编程工具的屏幕上下文输入工具

**面向谁：**

使用 Codex、Claude Code 或其他 Agent 编程工具的个人开发者、Vibe-coder、产品经理和小微创业者。

**解决什么具体问题：**

用户遇到界面问题、Bug 或设计细节时，需要反复截图、裁剪、上传、描述，才能让 AI 理解当前屏幕。产品将“我指向哪里”和“我说了什么”直接转换成 AI Agent 可用的上下文。

**使用场景：**

- 指向网页上的报错区域，让 Agent 判断问题。
- 指向某个 UI 元素，让 Agent 修改对应代码。
- 在本地模拟器或浏览器中指出视觉问题，减少复制粘贴和文字描述。
- 将屏幕区域与语音或文字指令一起发送给 Codex、Claude Code 或 MCP Agent。

**为什么今天：**

一方面，TrustMRR 上已有类似产品 Supamaus，用一次性付费模式验证了“屏幕指向 + Agent 上下文”这一窄场景；另一方面，Marc Lou 展示了 Codex 从生成代码到完成 iOS 提交的完整交付链路。AI 编程工具越能独立执行，用户越需要更高效地把现实屏幕状态交给 Agent。

**为什么适合枫：**

方向足够窄，可以先做浏览器截图、区域标注和文本指令拼接，不需要训练模型，也不需要囤货或大额投入。目标用户就是 AI 编程学习者和个人开发者，容易通过内容展示真实使用过程，并同时产出产品验证和小红书/公众号选题。

**2 小时验证动作：**

1. 做一个极简落地页，标题直接描述结果：“框选屏幕，直接交给 Codex/Claude Code”。
2. 放一个 30 秒使用流程：框选区域 → 输入问题 → 复制结构化上下文。
3. 设计三个候选入口：
   - 浏览器截图与框选。
   - 本地应用截图与框选。
   - 截图 + 语音/文字指令。
4. 面向 AI 编程学习者和独立开发者发出问题：  
   “你最近一次需要向 AI 解释屏幕内容时，花了几步？如果能框选后直接发送，你愿意试吗？”
5. 记录用户具体描述的工作流，不先开发完整桌面端。

**验证成功标准：**

- 至少收集 5 个目标用户的真实案例。
- 至少 3 人能描述最近发生过的“截图、解释、反复沟通”问题。
- 至少 2 人愿意提供一次真实任务测试。
- 用户优先选择同一个入口，而不是三个方向平均分散。

**周末能扩成什么：**

做成浏览器扩展或本地轻客户端：框选屏幕区域、OCR/截图、附带文字或语音指令，输出适合 Codex、Claude Code 或 MCP Agent 使用的上下文格式。先保留人工复制粘贴，不急于接入多个 Agent API。

## 今日 Top 3 信号

### 信号 1

**信号类型：** 技术趋势

**白话说：**

AI 编程工具正在从“帮你写代码”向“替你完成发布流程”推进。用户的瓶颈会逐渐从代码生产转向任务描述、屏幕理解和结果验收。

**证据：**

- 来源 A：Marc Lou 称 Codex 通过一次提示完成了一个新的 iOS App，并自动处理 App Store 文案、截图和提交流程。[查看原始帖子](https://x.com/marclou/status/2081721767366967757)
- 来源 B：OpenAI 发布研究，称 ChatGPT 用户正在跨越原有岗位边界承担更多工作任务。[查看原始研究](https://openai.com/index/how-ai-is-expanding-what-people-do-at-work)

**产品理解卡：** 不适用。

**为什么值得关注：**

如果 Agent 已经可以执行较长的交付链路，输入质量和上下文传递就会成为新的效率瓶颈。单纯做“AI 生成代码”的产品容易被基础模型能力覆盖，围绕真实操作界面做输入和验收工具，可能更容易形成具体工作流。

**对枫的启发：**

内容选题可以从“我只给一句话，Codex 如何完成 App 发布”进一步拆成：“AI 已经能提交 App 了，但为什么还需要人描述屏幕？”这类内容既能展示工具变化，也能自然引出产品验证。

**反向证据：**

Marc Lou 的案例是单个公开展示，不能证明普通用户都能稳定复现。自动提交 App 可能依赖特定环境、权限和账号配置，不能直接把演示效果当作普遍生产力提升。

### 信号 2

**信号类型：** 产品案例

**白话说：**

Supamaus 把“看到屏幕上的哪里”和“用户说了什么”直接交给 AI Agent，产品不试图成为通用开发平台，而是解决 Agent 使用中的一个具体输入问题。

**证据：**

- 来源 A：Supamaus 的公开产品描述是让 AI Agent 看见屏幕并采取行动，目标用户包括开发者、设计师、Vibe-coder、产品经理和创业者。[查看 TrustMRR 产品页](https://trustmrr.com/startup/supamaus)
- 来源 B：产品详情称 Supamaus Lite 可以把用户指向的内容和语音直接发送给 Claude Code、Codex 或 MCP Agent，并强调设备端处理、无需 API Key。[查看产品详情](https://trustmrr.com/startup/supamaus.md)

**产品理解卡：**

- **它是什么：** 面向 AI Agent 的屏幕上下文输入工具。
- **目标用户：** 开发者、设计师、Vibe-coder、产品经理、创业者，以及使用 Agent 的其他用户。
- **解决的痛点：** 用户不必手动复制、粘贴或描述屏幕内容，就能把指向的屏幕上下文传给 Agent。
- **核心功能或交付：** 通过屏幕指向和语音，把上下文发送给 Claude Code、Codex 或 MCP Agent；公开证据还提到设备端处理。
- **典型使用场景：** 公开证据未说明。
- **已知商业数据：** TrustMRR 页面显示收入 $374、售价 $28k、倍数 6.2x；每个数字均来自该产品的 TrustMRR 公开页面。
- **证据边界：** 公开资料没有说明活跃用户数、收入持续时间、获客渠道、留存或中文市场需求；收入和售价不能单独证明产品适合复刻。

**为什么值得关注：**

它符合“一人配合 AI 编程、一周内做出 MVP”的方向：核心价值不是训练模型，而是减少上下文输入步骤。产品也容易演示，适合转化为“一个真实 Bug 如何被 Agent 处理”的内容。

**对枫的启发：**

可以先验证“屏幕框选 + 结构化文本输出”，不要一开始复制完整桌面端。中文市场的差异化入口可以是更适合中文用户的提示模板、浏览器插件和本地开发环境教程。

**反向证据：**

公开收入只有 $374，不能说明需求已经被充分验证。产品可能依赖桌面权限、系统兼容性和 Agent 的具体接入方式；如果用户觉得截图上传已经够用，额外工具的付费意愿会很弱。

### 信号 3

**信号类型：** 平台变化

**白话说：**

中文市场正在出现把多个 Agent 产品线整合成统一办公入口的动作。对个人开发者来说，机会可能不在再做一个通用 Agent，而在围绕具体职业或场景做轻量工具和工作流。

**证据：**

- 来源 A：卡兹克称阿里将 QoderWork、悟空、MuleRun 三条 Agent 产品线整合为“千问办公”，并开始内测。[查看原始帖子](https://x.com/Khazix0918/status/2081659248384020846)
- 来源 B：OpenAI 研究显示，AI 用户正在使用 AI 承担跨岗位、跨任务的工作。[查看原始研究](https://openai.com/index/how-ai-is-expanding-what-people-do-at-work)

**产品理解卡：** 不适用。

**为什么值得关注：**

如果平台厂商持续把 Agent 能力收拢到办公入口，通用聊天、通用任务执行和通用办公助手会越来越难形成差异。个人开发者更应寻找平台不会优先覆盖的细分输入、交付和验证环节。

**对枫的启发：**

中文 AI 变现内容可以围绕“通用 Agent 上线后，个人开发者还能做什么”展开，重点讲具体工作流：餐饮门店内容、个人开发者发布、表格分析、客户资料整理等，而不是泛泛介绍某个模型。

**反向证据：**

目前输入只有一条社交媒体消息，且描述的是内测，无法确认产品是否正式发布、功能是否稳定或用户规模。阿里平台的能力和资源也可能迅速覆盖大量细分场景，个人产品需要避开其核心能力范围。

## 机会拆解

- **痛点：** AI 编程用户把屏幕状态传给 Agent 时，仍需要截图、裁剪、上传和文字解释。
- **明确买家：** 个人开发者、Vibe-coder、设计师、产品经理和小微创业者。
- **已有替代：** 系统截图、剪贴板、浏览器开发者工具、手动上传图片、直接文字描述。
- **小产品入口：** 浏览器框选截图 + 文字指令 + 结构化上下文复制，不先做全自动 Agent 执行。
- **可验证数据：** 真实用户案例数、愿意试用人数、同一场景重复出现次数、用户完成一次任务所需步骤、愿意付费或推荐的用户数。
- **风险：** 系统权限和跨平台兼容性；不同 Agent 的上下文格式不同；截图方案可能已足够好；公开案例的收入规模较小，不能证明市场足够大。

## 反向视角

这件事可能不值得做，原因有三：

1. Codex、Claude Code 和操作系统本身可能逐步加入屏幕理解能力，独立工具容易被内置功能替代。
2. 用户可能只在偶发 Bug 场景使用，频率不足以支撑订阅模式。
3. Supamaus 的公开收入规模有限，说明“有人买”与“值得做成产品”之间仍有距离。

因此，今天的目标不是开发完整产品，而是确认目标用户是否存在高频、重复、愿意真实测试的屏幕上下文问题。
