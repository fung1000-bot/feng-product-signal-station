# 枫的产品信号站 - 2026-09-22

## 今日主判断

最值得验证的不是再做一个通用 AI 应用，而是做一个面向 AI 编程用户的“工作流防丢层”：保存上下文、监测会话额度、支持安全分叉，并把一次开发过程沉淀为可复用资产。

## 今日最值得做的一个方向

**项目名：**  
中文 AI 编程上下文保险箱

**面向谁：**  
使用 Claude 或其他 AI 编程工具、经常遇到上下文过长、会话中断、提示词丢失和错误分支污染的个人开发者。

**解决什么具体问题：**  
AI 编程过程中，用户可能在会话被截断前失去上下文；尝试新方案时又容易破坏原本有效的对话。产品帮助用户保存提示词和关键上下文、监测使用量、在尝试新思路前分叉会话，并在中断后恢复工作。

**使用场景：**  
- 开发到一半，担心 Claude 会话即将达到限制。  
- 想尝试一个激进方案，但不想破坏当前有效的开发线程。  
- 想把一次成功的提示词、上下文和修复过程保存下来，下次继续使用。  
- 发布 AI 编程教程时，把真实开发过程整理成可复用模板。

**为什么今天：**  
TrustMRR 上的 ClaudeKit 已经把“会话中断和上下文丢失”包装成独立产品；OpenAI 同期强调让 AI agent 使用企业文件中的机构记忆。两条证据共同指向一个变化：AI 工具的瓶颈不只是生成能力，也包括长期上下文、工作过程和知识资产的保存。

**为什么适合枫：**  
它直接面向 AI 编程学习者和个人开发者，MVP 可以先从浏览器扩展或桌面剪贴板工具开始，不需要囤货、物流或大额前置投入。开发过程本身还能转化为小红书和公众号内容。

**2 小时验证动作：**  
1. 做一个单页原型，只承诺三个功能：  
   - 会话内容一键保存。  
   - 上下文长度或会话状态提醒。  
   - 一键复制“恢复上下文提示词”。  
2. 用一个真实 AI 编程任务测试：分别记录正常对话、主动分叉和恢复上下文所需的步骤。  
3. 写一篇验证型内容，标题可用：  
   - 《AI 编程最容易被忽略的坑：不是不会写，而是上下文丢了》  
   - 《我做了一个 AI 编程“存档键”，看看能不能避免重来》  
4. 观察是否有人主动询问“能不能使用”“什么时候开放”或愿意提交自己的会话痛点。

**验证成功标准：**  
至少有 5 名目标用户愿意描述自己遇到过的上下文丢失问题，其中至少 2 人愿意试用原型；同时，原型能让一次中断后的恢复过程少于 5 分钟。

**周末能扩成什么：**  
扩展为面向 Claude、ChatGPT 等工具的跨平台工作区：会话存档、提示词版本管理、上下文摘要、分支对比、项目级知识库和恢复模板。先不做复杂 agent 编排，优先解决“别丢、能续、可复用”。

## 今日 Top 3 信号

### 信号 1

**信号类型：** 产品案例

**白话说：**  
ClaudeKit 不是重新做一个 AI 编程助手，而是给 Claude.ai 加一层“工作保护”：在会话被截断前提醒用户，保存提示词、统计 token、分叉风险想法，并保护已有上下文。

**证据：**
- 来源 A：TrustMRR 将 ClaudeKit 描述为面向 Claude.ai 高级用户的工作保护层，核心功能包括 cutoff 提醒、会话分叉、提示词保存、token 统计和上下文保护。[TrustMRR - ClaudeKit](https://trustmrr.com/startup/claudekit-1)
- 来源 B：OpenAI 介绍 V7 时强调让 agent 使用分散在公司文件中的上下文，说明“可持续使用上下文”正在成为 agent 产品能力的一部分。[OpenAI - How V7 gives AI agents institutional memory](https://openai.com/index/v7)

**产品理解卡：**  
- **它是什么：** Claude.ai 的上下文与会话管理工具。  
- **目标用户：** Claude.ai power users。  
- **解决的痛点：** 避免 Claude 会话达到限制后丢失工作，并帮助用户保存上下文、分叉对话和管理提示词。  
- **核心功能或交付：** cutoff 监测、会话分叉、提示词保存、token 统计、上下文导出或保护。  
- **典型使用场景：** 公开证据未说明。  
- **已知商业数据：** TrustMRR 页面显示收入 $179、售价 $2.5k、倍数 1.2x，具体数据见 [TrustMRR - ClaudeKit](https://trustmrr.com/startup/claudekit-1)。  
- **证据边界：** 证据没有说明活跃用户、留存、付费转化、用户来源和各功能的实际使用频率。

**为什么值得关注：**  
这是一个足够窄、足够具体的 AI 编程配套产品。它证明用户可能愿意为“减少一次重做”付费，而不是只为更强的模型付费。

**对枫的启发：**  
产品机会：先做中文版、低复杂度的上下文保存与恢复工具。  
内容选题：把一次真实的 AI 编程中断、恢复、分叉过程做成实测内容。  
验证重点：不要先开发完整客户端，先验证用户是否愿意把会话存档和恢复当成刚需。

**反向证据：**  
- Claude 等平台可能逐步内置上下文管理功能，独立工具的差异化会被压缩。  
- 用户可能只在会话快结束时偶尔使用，不愿意持续付费。  
- 证据只显示产品挂牌数据，不能证明收入质量、增长趋势或产品仍在活跃运营。

### 信号 2

**信号类型：** 平台变化

**白话说：**  
AI 视频产品正在缩短从想法到上线的时间。OpenAI 将 Higgsfield 的案例描述为：借助 GPT-6 Astra，小企业可以更容易制作视频广告，Higgsfield 也能在一天内推出新的视频功能。Marc Lou 的公开动态则显示，他用游戏化活动分发 Higgsfield API credits，并鼓励已经做出产品的人展示成果。

**证据：**
- 来源 A：OpenAI 称 Higgsfield 使用 GPT-6 Astra 更快推出视频功能，并降低小企业制作视频广告的门槛。[OpenAI - Higgsfield from prompt to production with Astra](https://openai.com/index/higgsfield-from-prompt-to-production-with-astra)
- 来源 B：Marc Lou 表示向完成 escape game 的 30 人发放总价值 $30,000 的 Higgsfield API credits，并邀请已有产品的人展示作品；该帖显示 24,022 次曝光、132 个赞和 57 条回复。[Marc Lou on X](https://x.com/marclou/status/2102036799858028587)

**产品理解卡：**  
- **它是什么：** Higgsfield 的 AI 视频和视频广告创作产品。  
- **目标用户：** 小企业及需要制作视频内容的创作者。  
- **解决的痛点：** 降低视频广告和创意视频的制作门槛，加快从想法到成品的过程。  
- **核心功能或交付：** 公开证据未完整说明；OpenAI 案例确认其使用 GPT-6 Astra 推出新的视频功能。  
- **典型使用场景：** 小企业制作视频广告。  
- **已知商业数据：** 公开证据未说明。  
- **证据边界：** 公开证据没有说明 API 的成本、用户留存、视频效果或具体功能清单。

**为什么值得关注：**  
“模型能力更新”正在直接改变小产品的交付速度。对个人开发者来说，机会不一定是做底层视频模型，而是围绕一个具体内容场景，快速把生成能力包装成流程。

**对枫的启发：**  
内容选题：  
- 《AI 视频工具一天上线新功能，个人开发者还能做什么？》  
- 《不做模型，如何把视频 API 包成一个小产品？》  
- 《用 AI 编程做一个小企业视频广告生成器，2 小时能到哪一步？》

产品机会：把通用视频能力收窄为中文小微商家场景，例如“餐饮新品短视频脚本与素材生成流程”。但第一版应只验证一个内容类型，不要从完整视频工作室开始。

**反向证据：**  
- 视频生成赛道竞争激烈，单纯调用 API 很容易同质化。  
- API credits 或活动带来的使用量不代表稳定付费需求。  
- 内容生成的核心难点可能转移到素材版权、品牌一致性和投放效果，而不是生成本身。

### 信号 3

**信号类型：** 产品案例

**白话说：**  
Draftly 把“做一个沉浸式网站”压缩成一次提示词输入，目标是让创业者、餐饮店主、电商店主和独立开发者更快获得带 3D 效果的网站。

**证据：**
- 来源 A：TrustMRR 将 Draftly 描述为“用一个提示词构建沉浸式网站”，重点是 AI 生成 3D、电影式滚动网站。[TrustMRR - Draftly](https://trustmrr.com/startup/draftly-1)

**产品理解卡：**  
- **它是什么：** AI 3D 网站生成器。  
- **目标用户：** 创业者、电商店主、餐厅老板、独立开发者和自由职业顾问。  
- **解决的痛点：** 用更快、更低成本的方式替代传统网站制作中的高报价和长开发周期。  
- **核心功能或交付：** 通过单次提示词生成带沉浸式滚动效果的 3D 网站。  
- **典型使用场景：** 公开证据未说明。  
- **已知商业数据：** TrustMRR 页面显示收入 $31k、售价 $870k、倍数 2.4x，具体数据见 [TrustMRR - Draftly](https://trustmrr.com/startup/draftly-1)。  
- **证据边界：** 证据没有说明收入构成、用户数量、网站质量、生成成功率和客户获取方式。

**为什么值得关注：**  
它说明“AI + 网站交付”仍然可以通过强结果包装获得关注，但真正可复制的不是“再做一个网站生成器”，而是把网站生成能力绑定到一个明确行业和交付结果。

**对枫的启发：**  
产品机会：验证“中文小微商家单页生成器”是否比通用建站更容易成交。  
内容选题：  
- 《一个提示词做餐厅官网，AI 编程到底能不能替代外包？》  
- 《我把 AI 建站从“炫技”改成“能收款的落地页”》  
- 《给小商家做网站，最小 MVP 只需要哪 3 个功能？》

**反向证据：**  
- 网站生成器已经是拥挤赛道，视觉效果容易被模仿。  
- “生成网站”不等于客户愿意长期付费，域名、部署、维护和转化效果仍可能需要人工介入。  
- $31k 收入与 $870k 售价是挂牌页面数据，不能单独证明产品适合个人快速复制。

## 机会拆解

- **痛点：** AI 编程用户在长会话中会遇到上下文丢失、提示词不可复用、尝试新方案容易破坏原线程等问题。  
- **明确买家：** 高频使用 Claude 或其他 AI 编程工具的个人开发者、独立黑客、AI 编程学习者。  
- **已有替代：** 手动复制对话、截图、Markdown 存档、平台自带历史记录和普通笔记工具。  
- **小产品入口：** 浏览器扩展或本地工具，先做会话保存、恢复提示词和简单的分支管理。  
- **可验证数据：** 目标用户是否经历过上下文丢失；恢复一次任务需要多久；用户是否愿意持续保存会话；是否愿意支付低价订阅或一次性买断。  
- **风险：** 平台规则和页面结构变化；上下文数据的隐私与安全；平台未来内置类似功能；用户痛点频率不足以支撑订阅。

## 反向视角

这可能只是一个由单个产品挂牌页和平台叙事共同制造的机会错觉：

1. ClaudeKit 的公开收入规模较小，不能证明“上下文管理”已经形成大市场。  
2. 用户可能只需要偶尔手动复制内容，不愿意为一个辅助工具长期付费。  
3. OpenAI 关于机构记忆的叙事面向 agent 和企业文件，不等于个人 AI 编程用户会购买独立工具。  
4. 如果主要 AI 编程平台快速加入存档、分叉和上下文恢复能力，独立产品只能依靠跨平台、隐私、本地化或工作流集成建立差异。  
5. 因此，今天适合做的是用户访谈和原型验证，不适合直接投入完整产品开发。

## 今天不要追

1. **通用 AI 视频生成器**：已有工具和 API 竞争激烈，单纯换壳难以形成差异。  
2. **LinkedIn 自动放大和互动工具**：核心价值依赖平台分发和账号行为，存在平台规则与账号安全风险；当前证据也不足以证明适合中文市场。  
3. **公共记录驱动的房地产线索平台**：HarperAI 的模式依赖多源公共记录关联和专业销售场景，数据获取、合规和产品复杂度都不适合一周内验证。
